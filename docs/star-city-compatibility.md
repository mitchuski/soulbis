# Star and the City: integration boundaries

Source review, 7 September 2026. This accompanies the landing-page change; it does not implement or certify the VTA connection.

## Preserve the instrument

The Star is a geometric representation of the model, rather than a portfolio illustration. Keep its routes, vertex meanings, canonical key derivation and FIG-2.0 geometry. Lattice, Sigil and Skye remain complementary views. The requested small Star refinement changes panel labels, collapsible controls, touch/keyboard access and a read-only trace status. Its geometry, hashing and carrier/export routines are preserved. Mobile controls offer minimise, focus/exit and portrait export without a keyboard; narrow screens show one expanded panel at a time.

The local `star/index.html` and `lattice/index.html` already contain uncommitted work. In the current Star source, `buildExportCfg` spreads `CARRIED` before rebuilding reading fields, and `readyExportCfg` waits for loading to settle. Earlier observer notes about an unconditional allowlist loss are historical for this checkout. That source inspection alone does not establish a successful full round trip. The standalone sibling `star` repository must be reviewed independently; do not overwrite either twin from the other.

## What must carry across

- **City Key:** preserve supported and unknown extension fields through import, edits and export; re-derive κ under the existing canonical rules. Test unchanged exports, deliberate edits, prior lineage, packet roots, figures, walks and charts. A carrier is separate from a signing secret, holder authentication or delegated authority.
- **Geometry:** use versioned model coordinates and `SHAPE` semantics. Separate an agent instance, persona, knowledge item, promise, credential and evidence record. Display offsets do not create canonical model seats. Do not equate a 42-station learning fold with the 64-state model without its defined transform.
- **Private perspective:** feed only a disclosure-approved projection into a public renderer. Full VTA state and opaque carried extensions must not automatically become DOM, scene or network data. Switching observer or audience must clear prior private state. Stable κ and distinctive geometry may reveal relationships across encounters.
- **City permissions:** connect authenticated, fresh, audience-bound requests to current, scoped entitlements at the service. The current `mages_city/gate/permissions.mjs` denies when authentication and entitlement adapters are absent. An allowed preview remains distinct from an executed action and its receipt.
- **Time and evidence:** render illustrative, observed, signed, verified, unknown, expired and revoked states distinctly. A geometric horizon is not a measured security guarantee. A signature establishes only what its actual verifier checks.
- **Skye:** its source includes both full-key inspection and DH-PSI common-ground exchange. Neither a visible overlap nor an intersection result establishes delegation, admission, or authority. Review its actual supported statement and disclosure boundary before using it in the City workflow.
- **Cross-site passage:** the existing BroadcastChannel is same-origin. Ordinary hyperlinks are navigation, not a cross-domain key-transfer or permission protocol. Never append a key, private graph or VTA context to these landing-page links.

## Browser extension as the VTA expression

First Person direction: link the City Key to the browser-extension expression of the VTA, so sign-in selects the identity behind the visualisation and the journey records the agent's evolving state. This extends the guide and landing framing; it does not add a browser integration or change the Star renderer.

Proposed flow: authenticate with the extension, select and verify a City Key binding, request an audience-appropriate state projection, render that projection through the existing Star, and record approved results through the authorised state service. The next City Key version carries the permitted record and receipt references. Signing secrets, private agent state, presentation data and key-carrier content remain distinct.

Before enabling a connection button: pin the real extension API and supported browser/RP flow; bind session, principal, selected key version, origin/audience and expiry; enforce projection and write scopes at the service; clear prior view state on disconnect or account/community changes; deny a copied carrier, a substituted key, a replayed request and an unapproved write. A successful sign-in is not permission for every action. A local trace is not a service receipt.
